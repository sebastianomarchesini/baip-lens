# Privacy

BAIP Lens runs on your machine and writes files to your disk. This page lists what it reads, what it keeps, and where requests go.

## Principles

1. **Read-only.** The HTTP client allows only `GET` to the CF API. This is enforced per host by the egress allow-list in `packages/cli/src/net/allowlist.ts`, and unit tests prove it. A project scan of a folder (`baip-lens project --path`) only reads files; a project scan of a deployed app (`--cf`) sends only SFTP read requests over its SSH session. The one request a project scan makes about what it read is a lookup of public npm package names and versions on `api.osv.dev` (see [Project scans](#project-scans)); it changes nothing anywhere.
2. **No data leaves the machine**, with one exception that is said before it happens and can be turned off: a project scan sends the names and versions of the project's **public** npm packages to `api.osv.dev` to learn their known vulnerabilities ([Project scans](#project-scans)). The allow-list is the only way out, and redirects are never followed. There is no telemetry.
3. **No personal data** in any output.
4. **No secret values** in any output.

## Where requests go

**Used today: the first three rows by a Cloud Foundry scan, `api.osv.dev` by a project scan, and the last two with `project --cf`.** The other hosts are already in the allow-list for the rules of the next releases, so that adding a rule can never add a destination unnoticed, but nothing contacts them yet. **In progress.** A project scan now also asks `registry.npmjs.org` whether the public npm packages it kept are deprecated: one `GET /<package>/<version>` per package, then `GET /<package>/latest` for a package with a deprecated version, with no credential and nothing else of the project; of an answer only `version` and `deprecated` are read. `--no-dependency-check` turns that off too, and `--dependency-exclude` holds packages back from it as well. The answers are stored in the snapshot, but no rule reports them yet: the rule `DEP_DEPRECATED` and the full description on this page follow in the next change.

| Host | Why | What is sent | Status |
| --- | --- | --- | --- |
| Your CF API (`--api`) | inventory | `GET` only, with your token | 0.1.0 |
| Your UAA or login server (from the CF root) | sign-in, token refresh or client credentials | `POST /oauth/token` only | 0.1.0 |
| Your log cache (from the CF root, never guessed from the API host) | when each app last served a request (`APP_IDLE`) | `GET /api/v1/read/<app-guid>` only, with your token, for apps with an HTTP route | 0.3.0; `--no-traffic-check` turns it off |
| `api.osv.dev` | known vulnerabilities of the npm packages of a project (`DEP_KNOWN_CVE`) | `POST /v1/querybatch` with the names and versions of the packages your lockfiles resolved from the public npm registry, then `GET /v1/vulns/<id>` for each advisory it lists; no credential, nothing else of the project | `baip-lens project` (both modes); `--no-dependency-check` turns it off, `--dependency-exclude` holds packages back. Never by `baip-lens scan` |
| `endoflife.date` | runtime end-of-life dates | product names such as `nodejs` | planned |
| `ui5.sap.com` | UI5 maintenance status | a request for `/versionoverview.json` | planned |
| `registry.npmjs.org` | whether the npm packages of a project are deprecated (in progress: looked up and stored, not reported yet) | `GET /<package>/<version>` and `GET /<package>/latest` with the names and versions of the packages your lockfiles resolved from the public npm registry; no credential, nothing else of the project | `baip-lens project`; `--no-dependency-check` turns it off |
| Your app routes | the UI5 version served | one unauthenticated `GET /resources/sap-ui-version.json` per app, with no redirects; `--no-probe-routes` will turn it off | planned; 0.1.0 makes no request to app routes |
| Your UAA server (from the CF root) | the one-time SSH code, for `project --cf` only | `GET /oauth/authorize` with your token, as `cf ssh-code` does | `project --cf` |
| Your app SSH proxy (`links.app_ssh` from the CF root) | the files of the app you picked, or of each app of the project you picked, for `project --cf` only | one new one-time code per app as SSH password; then SFTP listing and read requests only | `project --cf` |

Your CF token is sent to the CF API and its log cache only, and with `project --cf` also to the UAA authorize endpoint, which hands out the one-time SSH code (as `cf ssh-code` asks for it). The allow-list knows which credential each host may receive: the CF token for those, the OAuth client id and secret for the token endpoint (never the CF token), and nothing for any other host: `api.osv.dev` gets no `Authorization` header and no cookie, from a client that does not know your CF API at all. The SSH proxy receives the one-time code as the SSH password, never the CF token. Unit tests check that no other host receives it, and that a credential a host may not receive is refused before anything is sent.

## What is kept

The snapshot and reports contain only allow-listed fields. The parsers drop everything else before it is stored.

- **Orgs and spaces:** GUID and name.
- **Apps:**
  - GUID, name, space, state, created and updated times, lifecycle type, and requested buildpacks.
  - Credentials in buildpack URLs are removed.
- **Current droplets:**
  - GUID, app, state, timestamps, stack, and the detected buildpack names and versions.
  - Detect output is cut to 200 characters.
  - For Docker droplets, the image reference with credentials removed.
- **Routes:** GUID, owning space, kind (`http`, `tcp`, `internal` or `unknown`) and the GUIDs of the destination apps, limited to the apps of the scanned inventory. Host, path, port and URL are not kept, nor annotations and labels. A destination that points to an app outside the inventory (possible with shared routes) is dropped, and a route with no destination left is not kept at all.
- **Web processes:** GUID, app, desired instance count, health check type and updated time. Never the start command.
- **App usage (`APP_IDLE`):** per app, a state (`idle`, `active`, `unknown` or `not_assessed`) with a signal and confidence, a reason code, or, for `active`, the time of the last request. All are fixed values except that one timestamp. The reports carry the same values: the Apps table, the `usage*` columns of the apps CSV and the JSON report.
- **Traffic history (`raw.history`):** per app, its GUID and its space's GUID, when the newest request any scan saw was written, when the current run of scans without a request began, and how many scans that run has. The list is in the snapshot only, but a `no_traffic` finding repeats these values (`scansWithoutTraffic`, `firstScanWithoutTraffic`, `silentSpanDays`, `lastRequestEverSeen`) in its evidence, so every report format carries them for that app. With `scan --previous`, the earlier snapshot is read from disk and validated, unknown fields are dropped, and only two things reach the new snapshot: these history values and the earlier scan's time (`options.previousScannedAt`, which the JSON and HTML reports carry too). An entry carries forward for an app still in the inventory, or unchanged for an app this scan could not see; it is dropped once a scan reads the app's space without the app. Nothing else of the earlier snapshot, such as its app names or findings, is carried.
- **Traffic (`raw.traffic`, snapshot only):** per app with an HTTP route, three values read from Log Cache: `lastRequestAt` (when the newest router access log was written, nothing about the request), `windowStart` (the oldest envelope Log Cache held for the app) and `envelopesExamined` (a count). A `no_traffic` finding repeats the window start and length in its evidence.
- **Findings:** rule id, severity, app reference, evidence (facts such as dates and versions), remediation and links.

## What is never kept

- **User identities:**
  - User names, emails and IDs are never stored.
  - Audit-event `actor` fields are dropped when the events are read.
  - App annotations and labels (which often hold owner emails) are not collected. The one exception is `project --cf`, which reads the six keys the deploy service writes to mark an app as part of a project and drops every other one (see [Deployed-app scans](#deployed-app-scans)).
- **Secrets:**
  - Tokens, refresh tokens and client secrets.
  - Environment variable **values**; with `--deep`, only variable names are kept.
  - Service credentials and service keys.
  - Droplet `execution_metadata` and start commands, and process commands (all of which can contain passwords).
- **Log lines.** The traffic check of `APP_IDLE` reads an app's log envelopes from Log Cache, and of each envelope it parses two things only: its timestamp and its `source_type` tag, which is checked for being `RTR` (and for being there at all) and then dropped. The access-log line (client address, request path and query, user agent, `X-Forwarded-For`, request id), the lines of every other log, every other tag (app, space and org names, addresses) and the instance are never parsed and never kept. Per app, only `lastRequestAt`, `windowStart` and `envelopesExamined` reach the snapshot. The same holds for the one envelope of any type read to find where the window starts, such as a router `http` timer whose tags carry the request's address, path and user agent. The leak test plants a client address, a request path, a query, a user agent and a request id in a router log (in its payload and in its tags) and in such a timer, plus app-log lines and tags on app logs, and fails if any of them reaches the snapshot, a report or what the scan prints while it runs.

A test scans the snapshot, every report format and the scan's progress output for planted secrets, emails, JWTs and credential URLs (`packages/cli/test/e2e/leak.test.ts`).

## Project scans

`baip-lens project --path <dir>` reads files of a local CAP or MTA project. It starts no child process and never runs `git`, and it makes **one kind of request**: it looks the public npm packages of the project's lockfiles up on `api.osv.dev` ([What is sent to OSV.dev](#what-is-sent-to-osvdev), below). With `--no-dependency-check`, or for a project without a lockfile or without a public package in it, such a scan makes no request at all. The allow-list of files it opens, and the files it never opens, are in [data-sources.md §8](data-sources.md#8-local-project-files-baip-lens-project).

What a project scan keeps:

- The relative file names of the recognised files it opened (`package.json`, `.cdsrc.json`, `.cdsrc.yaml`, `mta.yaml`, `xs-security.json`, `xs-app.json`, `*.cds`, seed `*.csv`, `*.html`, the npm lockfiles `package-lock.json` and `npm-shrinkwrap.json`, and the `.gitignore` files consulted for `*.mtar` archives), the names and sizes of `*.mtar` archives, the name of a root `yarn.lock` or `pnpm-lock.yaml` (listed, never opened), and for unreadable files the name and a reason code.
- Identifiers: the project id (the MTA id, else the package name without its scope, else the folder name), package names and version ranges of dependencies (a non-registry range such as a git or file URL is replaced by `[non-registry]`), module, resource, service, plan and buildpack names from `mta.yaml` (a buildpack is kept only as a name or as an http(s)/git URL reduced to scheme, host and path; a local path is dropped), scope, role-template and attribute names from the security descriptor, route source patterns from `xs-app.json`, and service, entity, element, action and role names from the CDS model.
- Counts and booleans: how many mocked users exist and how many carry a password, whether `restrict_all_services` or `audit-log` is configured, which authentication kind is set (as an enum, unknown strings become `other`), whether a route sets `csrfProtection`, whether an archive is git-ignored (also by the `.gitignore` files between the repository root and the project root, which are read but never stored), whether a `.git` entry exists in the project root or one of its ancestors, how many files were opened, and for seed CSV files the number of rows checked and, per sensitive column, its position in the header and the number of values that match a card, IBAN or secret check.
- From the npm lockfiles ([data-sources.md §12.1](data-sources.md#121-where-the-versions-come-from-)): for each package that the lockfile resolved from the **public npm registry** (`https://registry.npmjs.org`), its name and exact version, whether the root manifest or a workspace member lists it, whether it is installed for production, development or as optional, and which lockfiles pin it. For every other package (a company registry or mirror, git, a local file or folder, bundled, no known source, an invalid name or version) only a count per reason, and so for a public package whose name matches a pattern of `--dependency-exclude`. Per lockfile: its relative name, kind, format version and whether it could be read.
- From the answers of OSV.dev ([data-sources.md §12.3](data-sources.md#123-osvdev-)): per advisory its id, up to 20 other ids (CVE ids), a summary of one line, a CVSS vector and a severity label; per package version that has an advisory, the ids of its advisories and the fixed versions each names for that package. Nothing else of an advisory.
- From HTML pages: the line of the SAPUI5 bootstrap and its `src` reduced to origin and path for an http(s) URL (user info, query and fragment are dropped) or to the file name for a relative one, whether it is external, whether an `integrity` attribute exists (never its value) and the version form.

What a project scan never keeps:

- File contents, comments or doc strings, CSV cell values and CSV headers (only the positions of the columns that matched a sensitive pattern are kept, never a name), element types, defaults, titles and every annotation other than the recognised `@requires`, `@restrict.to`, `@readonly`, `@protocol`, `@cds.external` and `@PersonalData` markers.
- Mocked user names, passwords, roles and attributes (`cds.requires.auth.users` is only counted), destination names (only a hint such as `api` or `ui5-cdn` is derived from them), `description` fields, `oauth2-configuration`, `authorities`, `xsappname`, service keys, `properties`, `hooks`, `build-parameters` and `provides` of `mta.yaml`, and `VCAP_SERVICES`-shaped data.
- Absolute paths: every stored path is relative to the project root, the real path of the root is never written, the log prints counts and the project id only, and a collector error becomes a reason code rather than a message that could carry a path or file content.
- URLs with credentials: user info is removed from buildpack URLs and bootstrap sources.
- Anything of a lockfile entry that did not come from the public npm registry, its name included. Such a package is counted and never named: in no report, not in the terminal, in no request, and nowhere among the packages the snapshot keeps from the lockfiles, which are the only ones the lookup sends. Of a lockfile entry nothing but the name and version of a public package is kept: not the `resolved` address (it can name an internal host or carry a token), not `integrity`, not the `deprecated` message, not a license.
- **One exception, older than the lockfile step:** the names the root `package.json` lists under `dependencies` and `devDependencies` are kept in the snapshot (see "Identifiers" above), whatever registry they come from. A private package that is a direct dependency is therefore named in the snapshot file (`raw.projects[].packageJson`), though in no report and not in the terminal, and it is never looked up: the lookup does not read that list. `--dependency-exclude` does not remove a name from it either. The names under `optionalDependencies` and `peerDependencies` are used to tell direct from transitive packages and are not stored.
- Of an advisory: its details, its references and the people it credits (names and contacts). They are dropped when the answer is read. The summary is text that people outside your project wrote: before it is stored it is reduced to one line of at most 200 characters, without control or invisible characters, and what can carry a credential or name a person is taken out by its shape (the userinfo, the query and the fragment of an address that starts with a scheme such as `https://` are removed; a JWT, the value after `bearer` or `basic`, the value after `name=` for a name that is or ends in token, secret, api_key, apikey, passwd, password or passcode (`api_key=…`, `authToken=…`, `DB_PASSWORD=…`), the value after `password:`, `passcode:`, `client_secret:`, `access_token:` or `refresh_token:`, and an e-mail address are replaced; not recognised are a key that stands in the text with nothing that names it, a value after a colon for any other name, and the query of an address written without a scheme).
- The patterns of `--dependency-exclude`, which may name a private scope: they are written to no snapshot and no report and are not printed, also not in an error about a pattern that is not one.
- Files that typically hold credentials are never opened: `.cdsrc-private.json`, `.cdsrc.js`, `default-env.json`, `.env*`, `.npmrc`, `*.mtaext`, `*-key.json`, `*.pem`, `*.key`, `*.http`, `manifest.json`, `*.md`, and everything under `node_modules`, `.git`, `gen`, `dist`, `target`, `build`, `coverage` or any dot-directory. For a deployed app one file under `node_modules` is read, the lockfile of the installed tree (see [Deployed-app scans](#deployed-app-scans)); for a local folder none is.

The acme-incidents fixture plants a poison value in every one of those places (its lockfile, written at test time, holds a package from another registry with a token in its address, a git package, a linked folder, a bundled package, one without an address and one with an invalid version, plus planted `integrity`, `license` and `deprecated` fields), and `packages/cli/test/e2e/project.test.ts` fails if any of them, an absolute path or the temporary folder name reaches the snapshot, a report or the terminal.

### What is sent to OSV.dev

[OSV.dev](https://osv.dev) is a public database of known vulnerabilities in open-source packages, run by Google. To learn whether a package version your project installs has one, BAIP Lens has to ask about it by name. In plain words:

- **What is sent:** the name and the exact version of each npm package that a lockfile of the project resolved from the **public** npm registry (`https://registry.npmjs.org`), for example `express` and `4.19.2`. Each package once per scan, in one request per 1,000 packages; then one request per advisory OSV.dev listed, which carries only the id OSV.dev itself just gave.
- **What is not sent:** anything else. No package from a company registry or mirror, from git, from a local file or folder, bundled into another package or without a known source: the scan never kept those names, so it has none to send. Not the names in your `package.json`, no file name or path, not the name of the project, the app, the space or the org, no token, no cookie. The request carries a fixed `User-Agent` (`baip-lens/<version>`) and nothing that identifies you beyond what every HTTPS request shows the other side: your network address.
- **What OSV.dev can learn from it:** that someone at your address uses these public packages in these versions.
- **It is said first.** Before the first request the terminal prints `Looking up <n> public npm package(s) on api.osv.dev: only their names and versions are sent (--no-dependency-check turns this off, --dependency-exclude holds packages back)`. With `--quiet` nothing is printed about it and the lookup is still made; `--no-dependency-check` is what turns the lookup off.
- **`--no-dependency-check`** makes no request about a package at all. The HTML, JSON and SARIF reports, the snapshot and the terminal then say that the packages were not looked up (the check `collect.osv` and the rule `DEP_KNOWN_CVE` are recorded as skipped), never that nothing was found. The two CSV files list findings and apps only and carry no check, so a CSV on its own does not show whether the lookup ran.
- **`--dependency-exclude <list>`** holds packages back by name or pattern, for example `--dependency-exclude '@acme/*,acme-billing'`. Use it for a private package that is published on npmjs.com: it resolves from `registry.npmjs.org` like a public one, so its name would be sent. A package that matches is not kept from the lockfiles at all: it is not sent, and it is counted as `excluded` without its name. (A name your root `package.json` lists stays in the snapshot file, as said above.)
- **When OSV.dev cannot be reached**, the scan finishes with its other findings and says in the HTML, JSON and SARIF reports, in the snapshot and in the terminal that the packages were not looked up (the CSV files carry no check, as said above). Nothing is retried later and nothing is queued.
- **What comes back** is stored in the snapshot as listed above, so `baip-lens report --from` shows the same findings again without asking anyone.

Tests look at every request such a scan makes and fail on any host but `api.osv.dev`, on an `Authorization` or `Cookie` header, and on any planted private package name, token, path or project name in an address or a body (`packages/cli/test/e2e/project-dependencies.test.ts`, `project-cf.test.ts`). ⚠️ Looking packages up for deprecation on the npm registry is not built yet ([data-sources.md §12.4](data-sources.md#124-npm-registry-)); nothing is sent to the registry.

## Deployed-app scans

`baip-lens project --cf` applies the project scan above to a deployed app, or to every app of a deployed MTA project: the same files are opened (and the same ones never are), with one more, the npm lockfile of the installed tree (below); the same values are kept, and the same ones never are. The difference is where the files come from: they are read live from one running instance of each app over SSH, with the SFTP file channel and read requests only ([data-sources.md §10](data-sources.md#10-deployed-apps-baip-lens-project---cf) and [§11](data-sources.md#11-deployed-mta-projects-project---cf-picker)).

- **Nothing is downloaded to disk.** File contents are held in memory until the parsers have reduced them to names and counts; only the snapshot and the reports are written.
- **The one-time SSH code** is used once as the password and never printed or stored; each app of a project gets a new one. Your CF token goes to the CF API and to the UAA authorize endpoint only; `project --cf` does not read Log Cache.
- **The lookup on OSV.dev** is the same as for a folder ([What is sent to OSV.dev](#what-is-sent-to-osvdev)): the names and versions of the public npm packages the apps have installed, each once for the whole run, after the last SSH session is closed. It is made by a client of its own that cannot send your CF token or the one-time code, and it names no app, space or org.
- **The paths are relative** to the app folder (`/home/vcap/app`), as for a local project; the container path is never written to a report, and no reason of a skipped check names it.
- **One more file: the lockfile of the installed tree.** For a deployed app BAIP Lens asks for `node_modules/.package-lock.json`, the lockfile npm wrote for the packages it installed in the container, and reads it in place of the `package-lock.json` that was pushed with the app, which is then not opened. It is the only path under `node_modules` that is ever asked for: the folder itself is never listed, no other file in it is opened, and `.npmrc` is never asked for. On Cloud Foundry `node_modules` is usually a link to a folder next to the app folder, so this one file can lie outside `/home/vcap/app`, in the same container ([data-sources.md §10.2](data-sources.md#102-differences-from-a-local-folder)). What is kept of it is what is kept of every lockfile: the name and version of each package that was resolved from the public npm registry, a count per reason for all others, and nothing else of an entry. When the file is not there or cannot be used, the pushed lockfile is read without its development packages, which a deployed app does not install: those are neither kept nor counted. The snapshot lists the file as `node_modules/.package-lock.json` among the files read; no finding points to it. All apps of one project run together keep at most 20,000 packages. A test with a real SSH server plants a private package with a token in its address in the lockfiles of the containers, and a token in `.npmrc`; it fails if `.npmrc` or any other path under `node_modules` is asked for, or if a planted value reaches the terminal, the snapshot or a report.
- **Which app it was.** Per app read, the snapshot keeps the app name and, when the app was deployed as part of an MTA project, the MTA ID, version, module name and namespace (`raw.projects[].deployment`). The reports name the app by its project id: the app name, or an id derived from it when the name has characters an id cannot have.
- **Labels and annotations.** Of each app in the list, only six keys are read: the labels `mta_id` and `mta_namespace` and the annotations `mta_id`, `mta_version`, `mta_namespace` and `mta_module`. Every other label and annotation is dropped when the list is parsed, and a value is used only when it matches a strict pattern (identifiers, no free text), because anyone who may update an app can write these values. A test plants an e-mail address in another annotation and fails if it reaches the terminal, the snapshot or a report.
- **The app list** shown in the terminal (app and project names, and why some apps cannot be read) is not written anywhere, with one exception: when you read a project, each of its apps that was not read is recorded as a skipped check, with the app name in its title and a fixed reason (for example that it is stopped), so that the report says what it does not cover. The reason repeats no name and no cf command: the space name and the advice on what to do (`cf start <app>`, `cf allow-space-ssh <space>`) stay in the terminal.

## Side effects in your landscape

`GET` requests do not change anything. Two kinds of read are audited by Cloud Foundry:

- With `--deep`, reading an app's environment variables creates an `audit.app.environment_variables.show` event for that app.
- `project --cf` opens an SSH session to the app you pick, or one session to each readable app of the project you pick, one after the other. Cloud Foundry records each as `audit.app.ssh-authorized` (a refused login as `audit.app.ssh-unauthorized`, which BAIP Lens avoids by checking your role first, and by stopping a project run when the first login is refused instead of trying every app).

Tell your security team before you run `--deep` or `project --cf` scans.

Reading Log Cache creates no audit event, but it is not free: for each app, Log Cache asks Cloud Controller, with your token, whether you may read the app (`GET /v3/apps/<guid>`), which counts once per app against your CF API rate limit.

## User-level usage (v0.2)

Usage per user is not collected in v0.1. When it arrives in v0.2, it will be opt-in. User identifiers will be hashed with a random salt created for each scan and never stored, and only aggregated counts will be reported.

## Retention

Snapshots and reports are ordinary files in your `--out` folder. Delete them when you no longer need them. BAIP Lens keeps no other copy.
